Forge4D 深度调研：动态 3DGS 流式推理该选哪条路线

若目标是通用单路视频的真在线动态 3DGS，StreamSplat 比 Forge4D 和 VGGT 几何流方案更直接；若输入是四路同步稀疏相机且主体是人/人-物交互，Forge4D 的多视图质量与 novel-time 设计更合适，但当前公开代码与权重尚不足以直接部署。

核心结论

Forge4D 直接输出逐时刻 3D Gaussian 属性、相邻帧双向 3D motion 和自由时间融合结果，任务匹配度明显高于只输出 pose/depth/point map 的 StreamVGGT、OVGGT、LongStream。
Forge4D 的真实新观测更新率是 4.45 FPS（224.27 ms/关键帧，H20、4×518²）；44.42/88.48 FPS 是在相邻关键帧之间加入 10/20 个廉价插值输出，不能当作 44/88 FPS 的新场景重建。
StreamSplat 面向单路非标定一般动态视频，维护 persistent Gaussian state，论文报告 A100 上 49 ms/帧（约 20.4 FPS），并公开 checkpoint；因此它是未限定场景时更适合的默认起点。
Forge4D 更适合四路同步人像/人物交互：高质量多视图覆盖、metric-scale 目标、novel-view + novel-time；但训练域集中于人体，不能直接外推为通用动态场景模型。
当前 Forge4D 仓库无预训练权重，demo 每帧重新初始化 state token，并依赖数据集 GT 相机计算尺度/渲染；复现前需要修正代码路径并自行训练。

先给选型答案

“动态 3DGS 流式推理”没有单一最优解；真正决定方案的是输入相机形态、主体域、是否要求度量坐标和新状态更新率。

默认未限定场景时，我建议 StreamSplat。 它从单路非标定视频逐帧编码当前观测，利用前一帧特征预测双向 deformation，把新旧 Gaussians 更新到 persistent Gaussian state；其输出本身就是可渲染动态 3DGS，而不是需要二次转换的 point/depth。

如果是四路同步相机的人体或人-物交互，建议 Forge4D。 它继承 VGGT 的多视图几何先验，直接预测 pixel-aligned Gaussian 属性，并用固定 state tokens 对齐时间尺度，再对相邻关键帧预测逐 Gaussian 双向 motion 与遮挡感知融合。它在 novel-view/novel-time 的人体质量上明显强于更通用的两帧模型。

不建议直接用 OVGGT 或 LongStream 作为最终动态 3DGS 模型。 它们解决的是在线 pose/depth/point map 与长程几何记忆，本身没有 Gaussian appearance、运动、可见性和生命周期建模。若产品必须同时具备 metric world map 与动态 3DGS，可将它们作为几何前端，但仍需要训练 Gaussian/motion/fusion heads。

Forge4D 实际做了什么

Forge4D 不是简单的 StreamVGGT + Gaussian head，而是把静态重建、跨时刻状态与逐 Gaussian 运动拆成三阶段训练。

Stage 1 以预训练 VGGT 为 backbone，在每个时间点联合处理同步稀疏视角，额外 DPT heads 输出 Gaussian position、opacity、color、rotation、scale，同时预测相机参数。论文加入 metric gauge regularization，用相机平移尺度对齐 VGGT 归一化几何与真实世界尺度。

Stage 2 用固定大小的 state tokens 压缩全部历史：当前四路图像先做 frame/global attention；state token 作为 K/V 向当前特征广播历史，同时作为 Query 读取当前特征并更新。相较 StreamVGGT 的随帧增长 KV cache，这是一种 O(1) recurrent latent state，更适合无限输入，但也更容易因压缩而忘记长程细节。

Stage 3 读取 t−1 与 t 的中间特征，预测每个 Gaussian 的 backward/forward 3D motion。两个关键帧的 Gaussians 按线性速度变形到中间时刻，再通过 occlusion-aware fusion 保留遮挡区、合并冗余 Gaussian，从而生成任意中间时间的 3DGS。

因此，Forge4D 的最终 4D 表示不是单一 canonical Gaussian + 一个全局 deformation MLP，而是每个输入时刻的 3DGS、相邻帧双向运动场和融合函数的组合。这种表示对短间隔人体动作很自然，但线性速度假设在大时间间隔会退化；论文补充材料报告间隔增大时 PSNR 最多下降 3.04 dB。

不要把插值 FPS 当成重建 FPS

Forge4D 的高帧率数字适合描述播放/输出速率，不适合描述新场景信息被吸收的速率。

论文 Table 6 将计算拆开：关键帧 3DGS 重建 176.50 ms，motion prediction 47.77 ms，full model 合计 224.27 ms，即 4.45 个新动态状态/秒。中间 10 个插值只增加约 1.46 ms，因此输出可升到 44.42 FPS；20 个插值则为 88.48 FPS。

这不是作弊：在体积视频播放、自由视角回放或慢动作系统中，插值帧本来就是有价值的。但如果需求是机器人感知、在线编辑或新动作立即反映到 3D 状态，真正的系统频率仍是约 4.45 FPS，并且需要等待当前与前一关键帧来估计双向运动。

补充 Table 11 的 39.72 FPS 同样标注为 Forge4D (+20 interp.)；不能把它与 StreamSplat 的每个输入帧 49 ms 直接等价比较。

工程口径建议

分别记录 ingest FPS（新相机帧进入模型）、state-update FPS（新 3DGS 状态完成）、render FPS（同一状态渲染多个视角）和 synthesized-output FPS（插值帧）。只报最后一项会严重高估在线感知能力。

为什么通用动态场景更推荐 StreamSplat

StreamSplat 从任务定义上就是单路非标定动态视频的逐帧 3DGS 状态更新，而不是把多机位人体模型泛化到一般场景。

StreamSplat 每帧先结合外部 pseudo-depth 编码静态 Gaussians，再用当前与前一帧 embedding 预测双向 velocity 和随时间变化的 opacity。persistent Gaussian state 会更新已有内容、添加新出现的 Gaussians，并在当前时刻把 opacity 已消失的 primitives 清理掉。

其 online algorithm 只保留上一帧 feature 与持续 Gaussian 状态，输入未来不可见；论文声称可处理任意长度。A100、288×512 下端到端 49 ms/帧，其中 encoder 18.8 ms、decoder 18.4 ms、rasterization 4.0 ms、预后处理 7.8 ms，对应约 20.4 FPS 的真实新观测处理率。

它的代价也很明确：为了绕过未知相机，采用 orthographic canonical space，并把 camera motion/perspective effects 吸收到 Gaussian dynamics；所以它不是严格的 metric world-space 重建，近距离强透视会失真。动态 decoder 只看两帧，论文也承认快速运动或长遮挡时会丢失更早信息。

因此 StreamSplat 更像“通用动态视频 → 连续可渲染 3D 状态”的实时基线；Forge4D 更像“同步多机位人体 → 高质量 metric-ish 体积视频与任意时间插值”的专用模型。

Forge4D 当前公开代码：设计值得借鉴，但还不是开箱即用实现

论文方法判断与代码可部署性必须分开；截至本次核查，Forge4D 的公开仓库存在三项直接影响 streaming demo 的缺口。

第一，README 明确显示三阶段预训练 checkpoint 全部为 coming soon。仓库有训练代码和 inference demo，但用户必须自行准备 DNA-Rendering、训练三阶段模型，不能直接复现论文速度与质量。

第二，模型类本身正确地把第 t 帧返回的 updated_state_token 传给 t+1；但公开 runfiles/inference.py 在每个循环内重新从 model.state_token 初始化，然后只处理当前帧。这意味着 demo 没有实际累积历史 state，与 README 所述 streaming state 不一致。修复方式是在循环外初始化，并把上一步返回值继续传入。

第三，论文描述由 scale head 预测 metric gauge；当前代码没有这个 head。demo 读取数据集 GT extrinsics/intrinsics，使用预测/GT camera translation norm 的比值计算 scale，再用 GT cameras 渲染。仓库自己的 PAPER_CONSISTENCY.md 也记录了这一差异。因此“uncalibrated、metric-scale deployment”在当前公开代码中尚未闭环。

另外，论文写作中的“a state token”在代码中实际是每层 1024 个 state tokens，共 24 层；这是固定大小、不会随时间增长，但并不是一个轻量标量式状态。仓库一致性文档还记录了 stage-3 optimizer、flow loss、zero-init、学习率和冻结范围等论文/原始实现差异，其中部分已在当前仓库修复。

推荐落地路线

如果今天开始做，我会先用最接近目标的动态 3DGS 模型闭环输出，再补几何与长程状态，而不是从纯 VGGT geometry 模型开始重造 Gaussian 动态头。

  • 通用单路动态场景 MVP： 以 StreamSplat 为主线，先复现 49 ms/帧基线；增加 camera/intrinsic head 或接轻量 VGGT/LongStream pose 前端，逐步从 orthographic canonical 升级到 perspective metric space。
  • 四路同步人体体积视频： 采用 Forge4D 的 Gaussian/motion/fusion 设计；先修复 state carry 和 gauge 路径，再训练权重。显示端可利用 10–20 个中间插值达到 44–88 FPS，但业务控制/编辑仍按 4.45 FPS 新状态设计。
  • 无限长人体直播： 在 Forge4D state token 上增加 LongStream 风格的 keyframe-relative gauge、周期 re-anchor/reset，并保留短期显式 Gaussian keyframe，避免单一压缩状态长期漂移。
  • 要求全局 metric map 与动态 3DGS： 使用 LongStream/VGGT-SLAM 产生稳定 camera/gauge，但 Gaussian motion/fusion 仍需像 StreamSplat/Forge4D 一样显式训练。不要假设 point map 可以零成本转成稳定动态 3DGS。

最终建议

在没有更多输入约束时，选 StreamSplat；确定是四路人像 capture 后再选 Forge4D。若团队坚持 VGGT 技术栈，建议借 Forge4D 的 Gaussian/motion heads，但用 LongStream 式相对坐标与周期刷新替换其长期状态策略。

局限与开放问题

  • Forge4D 与 StreamSplat 的速度测试硬件、分辨率、输入视角数和任务不同：H20/4×518² 对 A100/1×288×512，不能把 FPS 当作同条件排名。
  • Forge4D 论文的 metric-scale 与 uncalibrated 主张在当前公开 demo 中依赖 GT 相机；本报告因此把论文设计能力与代码现状分开。
  • StreamSplat 的 arbitrary-length 指资源与接口可持续，不保证长遮挡/快速运动后仍保留所有早期几何；其论文明确承认两帧窗口会丢更早信息。
  • 两者都主要做 feed-forward 重建和渲染，不等于完整 SLAM：回环检测、全局 pose graph、长期地图重定位仍需独立系统模块。
  • 如果目标包含大尺度动态背景、多个长期存在的独立物体、可编辑 object identity，还需要显式实例级生命周期与数据关联，现有两种方案均未完整解决。

证据与推断边界

  • 论文明示：Forge4D 三阶段结构、4.45 FPS full-model 更新率、插值输出率；StreamSplat 49 ms/帧、两帧 deformation 与 persistent Gaussian update。
  • 代码核查事实：Forge4D README 截至 2026-11-09 仍无 checkpoint；inference demo 在循环内重置 state；scale/render 路径使用 GT cameras。
  • 本文推断：将 StreamSplat 作为通用动态 3DGS 默认选项、将 Forge4D 作为多机位人体专用选项，是基于任务/接口匹配做的工程判断，不是论文作者的结论。
  • 混合 LongStream gauge/cache 与 Forge4D/StreamSplat heads 是架构建议，尚无对应端到端消融，不能视为已证实优于原方法。
